# Security

This page says what memsilo protects, how, and, as importantly, what it does not. memsilo
is a small server you operate yourself. It is **not a finished SaaS**.

## Threat model in one paragraph

Your customers never talk to memsilo. Your **backend** does, holding **one bearer token per
customer** and calling memsilo on their behalf. memsilo's job is to make sure a request
made with customer A's token can only read, write or delete customer A's memories. It is
not designed to defend against a compromised backend, a compromised host, or a malicious
operator: all of those can read every customer's data.

## Isolation is logical

- All customers' memories live in **one Qdrant collection** (`qdrant.collection`, default
  `memsilo`). They are separated by a `user_id` filter that the server adds to every
  search, list, stats and add, using the id the token resolves to.
- There is no per-customer encryption key, no per-customer collection and no per-customer
  database. A bug in memsilo, Mem0 or Qdrant, or direct access to the Qdrant port (with its
  API key) or the Qdrant volume, bypasses the filter completely.
- Anyone who can read the Qdrant storage volume, `./data/history.db` or a backup sees every
  customer's memory text in the clear.

What the code does to keep the filter honest:

- **Every tool is scoped by the authenticated token.** No tool takes a `user_id`
  argument; the id comes from the token. There is no admin bypass and no "list all users"
  or "read as user X" tool: the server registers exactly five tools
  (`search_memory`, `add_memory`, `get_all_memories`, `delete_memory`, `memory_stats`).
- **`delete_memory` refuses other users' ids.** It looks the memory up and deletes only if
  its `user_id` equals the caller's; otherwise it answers
  `not found or not owned by you` and deletes nothing. Anything that is not a well-formed
  memory id (a lower-case UUID, as Mem0 mints them) gets the same answer without reaching
  Qdrant. After a delete it purges that memory's history rows from `history.db` and checks
  none is left; if that fails, the reply says the memory was deleted but cleanup failed.
- **`add_memory` rejects metadata that could re-label a memory:** it must be a JSON object
  and may not contain `user_id`, `agent_id`, `run_id` or `actor_id` (case-insensitive).
- **Search and list results are clamped:** `limit` on `search_memory` and `get_all_memories`
  is forced into 1-200. `memory_stats` takes no limit: it counts at most 100,000 of one
  customer's memories.
- **Request size:** the `mcp` library's transports refuse request bodies over 4 MiB with
  HTTP `413`. memsilo sets no smaller limit on `text` or `query`; if you need one, enforce
  it in your backend or proxy.
- **Errors carry no internals:** when Mem0 or Qdrant fails, the tool logs the exception on
  the server and the caller gets only `internal error`, never the library's message (which
  can name internal addresses such as the Qdrant URL).

## Tokens

- A token is `ms_<user_id>_<secrets.token_urlsafe(32)>`: **256 bits** from the operating
  system's CSPRNG, generated by the server. Only `sha256:<hex>` of it is stored in
  `users.json`; the token is shown once, when it is minted.
- **Unsalted SHA-256 is sound here only because tokens are server-generated and random.**
  A 256-bit random value cannot be brute-forced or dictionary-attacked, so a salt or a slow
  KDF would add nothing. This is **not** safe for user-chosen secrets, so memsilo never lets
  anyone choose a token. Do not add a feature that does.
- The `user_id` inside the token is not secret and is not what authenticates: the whole
  string is hashed and looked up.
- `revoke` stops a token working immediately (the store is read on every request);
  `rotate` replaces it. The store is rewritten atomically (temp file, `fsync`, rename)
  under an exclusive file lock, with mode `0600`.
- Use **opaque ids**: do not use phone numbers, names or email addresses as `user_id`. `add`
  without an id generates `cust_` plus 16 random hex characters. Keep the mapping to real
  people in your own backend.

## Sessions

On the HTTP transports a session belongs to the token that created it. A request that
names any session identifier (the `session_id` query parameter for SSE, the
`Mcp-Session-Id` header for streamable HTTP) is refused with `403` unless the server itself
issued that identifier to that same user. The check runs in memsilo's middleware and,
independently, inside the `mcp` library's transports. Requests with a missing, unknown or
revoked token get `401`. `/health` is the only unauthenticated path.

## Transports and network

- **`stdio` is unauthenticated and local-only.** It is a local process launch and acts as
  `MEMSILO_DEFAULT_USER_ID`. Never use it to serve customers.
- The default bind address is **`127.0.0.1`**. The provided compose file sets
  `MEMSILO_SERVER_HOST=0.0.0.0` *inside the container* and publishes the port on the
  host's loopback only (`127.0.0.1:8100`).
- **There is no TLS.** Tokens travel as `Authorization` headers; without TLS they are
  readable on the network. Terminate TLS in a reverse proxy (see the README) and never
  expose port 8100 directly.
- **Qdrant requires an API key in the provided compose file** (`QDRANT_API_KEY`, which
  compose refuses to start without, passed to Qdrant and to memsilo). It is not published on
  the host, but "not published" is not "unreachable": the container's address on the Docker
  bridge network is routable from the host, so local users and processes and other
  containers on the same Docker host can connect to it. We confirmed that before this change
  any of them could read every memory with a plain `curl`, and that with the key set Qdrant
  answers `401` without it or with a wrong one. Anyone who has the key and can reach the
  port can read and write every memory, bypassing all of the above: keep `.env` secret, and
  do not publish the port.
- **No rate limiting** and no per-customer quotas in memsilo itself. Add limits in your proxy or backend.
- Behind a same-machine proxy with the default loopback bind, requests with a public `Host`
  header are rejected with `421` by the `mcp` library's DNS-rebinding protection. See the
  README for the two fixes.

## Where customer text goes and stays

- **Mem0 sends memory text to the configured LLM provider** (Anthropic by default) to
  extract facts. What that provider retains is governed by its terms, not by memsilo.
- **Mem0's anonymous telemetry is off by default** (`telemetry: false`, and memsilo sets
  `MEM0_TELEMETRY` accordingly before Mem0 is imported, in both the server and the CLI).
  Other library telemetry is covered under [Network traffic](#network-traffic).
- Memory text is also stored in **Mem0's history database** (`storage.history_db`, default
  `data/history.db`), including the previous text of updated or deleted memories, and in
  Mem0's cached conversation messages. `delete_memory` and `erase` purge what they can
  trace; see the limits below.
- **Qdrant keeps deleted text on disk for a while.** Its deletes are soft: after an erase the
  text was still in the Qdrant volume (write-ahead log and segment payload file), and a
  restart did not remove it. In Qdrant 1.19.0 the vacuum that rewrites segments does not run
  for collections under 100 points. Treat the volume as containing erased data, encrypt it
  at rest, and see the README's erase section.

## Network traffic

With the provided image and compose file, and the settings below, the only outbound
connection memsilo makes is to **the configured LLM endpoint** (Anthropic by default), when
a memory is added. Everything else stays on the compose network (memsilo to Qdrant). What we
switched off, and how we checked it (onnxruntime 1.29.0, fastembed 0.8.0, Qdrant 1.19.0):

- **onnxruntime telemetry.** fastembed computes embeddings with onnxruntime, and onnxruntime
  1.29 starts Microsoft telemetry as soon as it is imported (which importing Mem0 does): it
  writes a device id and an event queue under `~/.cache/Microsoft/DeveloperTools/.onnxruntime`
  and uploads the events to Microsoft. The events we inspected carried no memory text
  (model-load, session and performance data). The switch is the environment variable
  `ORT_DISABLE_TELEMETRY=1`, read when onnxruntime is imported; calling
  `onnxruntime.disable_telemetry_events()` afterwards still leaves the import-time events
  queued. memsilo sets the variable before Mem0 is imported, in the server and the CLI, and
  the image sets it too. Checked: with it, no `.onnxruntime` directory is created, and while
  adding and searching the memsilo container had no TCP connection other than to Qdrant.
- **Hugging Face Hub.** fastembed fetches its models from Hugging Face. The image downloads
  both models Mem0 uses at build time (the `BAAI/bge-small-en-v1.5` embedder and the
  `Qdrant/bm25` encoder of Mem0's hybrid search) and runs with `HF_HUB_OFFLINE=1` and
  `HF_HUB_DISABLE_TELEMETRY=1`. Before this, the BM25 encoder was downloaded on first use
  after every container recreate, and Mem0 silently disables BM25 search when it cannot
  load it. Checked: both models load in a container with no network at all, and the server
  logs `BM25 encoder loaded`. A bare-metal run (`python mcp_server.py`) still downloads the
  models on first use unless you set `HF_HUB_OFFLINE=1` after caching them.
- **Qdrant telemetry.** Qdrant reports telemetry by default. The compose file sets
  `QDRANT__TELEMETRY_DISABLED`; Qdrant then logs `Telemetry reporting disabled`.
- Mem0 2.0.20 writes `~/.mem0/config.json` with a random anonymous id even with its telemetry
  off. It stays inside the container.

If you need certainty rather than our check, restrict the memsilo container's egress to
your LLM endpoint (for example with a firewall rule on the Docker host); nothing else in
memsilo needs the internet at runtime.
- **Erasure** (`manage_users.py erase <user_id> --yes --revoke`) deletes the customer's memories from
  Qdrant and purges that customer's rows from the history database (the history rows of the
  deleted memory ids, and the cached messages for that customer, using `secure_delete`).
  `erase` and `export` first refuse any id that is not a well-formed user id: Mem0's
  Qdrant store treats `*` as "match any user", so an unchecked `erase '*'` would erase
  everyone. After purging, `erase` re-reads the history database for the memory ids it
  collected in that same run, and Qdrant for the customer, and **fails (non-zero exit) if
  anything remains**, listing the memory ids. A later run cannot find those ids again once
  the memories are gone from Qdrant, so that failure is not fixed by re-running: purge the
  listed ids by hand (README, "Recovering from an incomplete erase"). Memories past a Mem0
  `expiration_date`, hidden from search and listing, are erased and exported too. Its
  limits:
    - `delete_memory` purges the history of what it deletes. Only history rows of memories
      that Mem0 itself deleted or merged **before** the erase can not be traced to a
      customer (the history table carries no user id), so their text may remain in
      `history.db`. Planned follow-up: prune history rows whose memory no longer exists.
    - **The Qdrant volume may still hold the erased text** (soft deletes, see above).
    - **Backups and Qdrant snapshots retain data** until you rotate them out.
    - **`users.json` keeps the customer's row** after `erase --revoke`: revoking sets
      `revoked: true`, and `user_id`, `display_name`, `created_at` and the token hash remain.
      Use a non-identifying `--display-name` (an internal customer number), never a real
      name or phone number.
    - If you install mem0ai's optional NLP extra (spaCy), Mem0 also keeps a
      `<collection>_entities` collection of entity names, which `erase` does not clean. The
      provided image does not include spaCy, so that collection is not populated.
    - `export` returns only current memories: not history rows, cached messages or the
      `users.json` row.
    - With the `anthropic` provider, `erase` and `export` need `ANTHROPIC_API_KEY` to be set
      (they construct the same Mem0 client as the server) but never call the LLM provider;
      a placeholder value works.

## Container and files

- The image runs as a **non-root user with the fixed uid/gid 10001**. A fixed id keeps
  `./data` ownership predictable; `users.json` is replaced atomically, so its owner is
  whoever ran the writer.
- `./data` is set to `10001:10001`, mode `700`, by the `data-init` compose service on every
  `docker compose up`. **Run the CLI as the container user** (`docker compose exec memsilo
  ...`), never as root: a root-written `users.json` is unreadable by the server, which then
  fails every authenticated request.
- Secrets (`ANTHROPIC_API_KEY`, `QDRANT_API_KEY`) are read from the environment only;
  a secret-looking key in `config.yaml` is a startup error. `.env` and `config.yaml` are
  git-ignored and excluded from the image build context.

## Reporting a vulnerability

Please report suspected vulnerabilities privately (for example through the hosting
repository's private vulnerability reporting, if enabled) rather than in a public issue.
Include the version or commit, what you did and what you saw.
